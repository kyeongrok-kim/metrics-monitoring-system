metrics-monitoring-system

책 159–168p의 개략적 설계안(그림 5.6)을 Kotlin과 InfluxDB 2.x로 축소 구현한 스터디 프로젝트입니다. 가상 서버가 지표를 보내면 수집기가 시계열 DB에 쓰고, 질의 서비스가 읽어 경보를 판단합니다. 아래 수치와 그래프는 모두 2026-10-22 실제 실행 결과입니다.

지표는 한 방향으로 흐르고, 경보는 질의로 되돌아 읽는다

  • 지표 출처서버 6대(풀 2개 × 3대). 각 서버가 CPU, 메모리, 초당 요청 수, MQ 메시지 수를 1초마다 생성합니다. 책 규모(풀 1,000개 × 100대)를 줄인 것입니다.
  • 전송 큐 → 수집기Channel이 Kafka 자리를 대신합니다. 수집기는 100건 또는 1초 중 먼저 차는 조건에서 한 번에 씁니다. 쓰기가 실패하면 버퍼를 남겨 두고 다음 flush에서 다시 씁니다.
  • 시계열 DB원본은 7일, 1분 단위는 30일, 1시간 단위는 1년 보관합니다. 다운샘플링은 InfluxDB Task가 맡습니다.
  • 질의 서비스 → 경보질의 서비스가 host별 최근 15초 평균을 조회합니다. 경보 관리자는 규칙을 평가해 상태가 바뀔 때만 알림을 보냅니다.

알림은 PENDING → FIRING과 FIRING → OK(RESOLVED) 두 번의 전이에서만 나갑니다. FIRING 상태로 계속 위반해도 다시 알리지 않습니다(중복 제거). PENDING 중에 정상으로 돌아오면 알림 없이 OK로 돌아갑니다. Prometheus 경보 규칙의 for 절과 같은 개념입니다.

설계 결정

무엇을 골랐고, 무엇을 남겨 뒀나

전송 큐: Kotlin Channel

실습에 필요한 인프라를 InfluxDB 하나로 줄였습니다. 데이터를 보내는 쪽과 쓰는 쪽을 분리하는 역할은 그대로 보여 줍니다.

보류안 Kafka · 수집기가 죽어도 데이터가 남고 소비자를 여럿 둘 수 있지만, 브로커 운영이 추가됩니다. 책 후반부를 공부할 때 이 부분만 바꾸면 됩니다.

수집 방식: Push

지표가 출처에서 DB까지 가는 흐름이 코드에 그대로 드러납니다.

보류안 Pull (Prometheus) · 서비스 탐색과 수집 대상 상태 확인이 쉽지만, 짧게 실행되는 작업은 놓칠 수 있습니다. 스터디 주제로 남겨 두었습니다.

경보: 연속 2회 위반 시 FIRING

순간 스파이크 하나로 경보가 잘못 울리는 것을 막습니다. 대신 감지가 1회 평가 주기(5초)만큼 늦어집니다.

보류안 즉시 발송 · 감지는 빠르지만 경보 피로(alert fatigue)가 커집니다.

다운샘플링: mean과 max 함께 보존

위 실험처럼 평균만 남기면 스파이크가 사라집니다. 1시간 집계의 "평균의 평균"은 근사값이라는 점도 Task 주석에 적어 두었습니다.

보류안 sum + count 보존 · 정확한 평균을 다시 계산할 수 있지만 저장량이 늘어납니다. 백분위수(p99)는 이 방식으로도 정확히 합칠 수 없습니다.
